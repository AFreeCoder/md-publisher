# 锦章一期设计：网页版（门户 + 在线排版）

状态：已评审，2026-09-10 定稿（issue #5）。2026-09-08 起草，2026-09-09 按用户决定改为 Next.js，同日合并 Codex 评审。上游：[需求文档](../../requirements/product-v1/requirements.md) 功能 2、17、25、29 与业务规则 6.1、6.2、6.3、7.3；过程记录在 [issue #5](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/5)（网页版）与 [issue #4](https://github.com/AFreeCoder/jinzhang-md-publisher/issues/4)（总体架构）。总体架构与 core 见 [architecture.md](architecture.md)，本文只写网页版这个壳，不另写一套转换规则。

## 1. 结论

- 网页版是一个 Next.js 应用（App Router，服务端模式）：门户首页加在线排版页，没有账号、数据库和文章上传。排版、预览、复制全部在浏览器里由 core 完成；一期的服务端能力只有图片中转的两个接口：签发上传条件、校验已上传对象并发放限时读取地址
- 复制路径按平台分两条：复制到公众号时图片以 data URL 内嵌进剪贴板 HTML，这是 my-toolbox 日常使用验证过的做法；复制到知乎时图片先经中转接口直传私有的阿里云 OSS 桶，剪贴板里放 7 天有效的预签名地址，知乎编辑器粘贴时把图片转存到自己的存储（作者用 my-toolbox 多次实际使用证实）
- 预览放在带 `sandbox` 的 `iframe` 里渲染，与页面样式隔离、不执行脚本；预览与复制使用同一份 core 输出
- 选 Next.js 而不是纯静态构建的理由：中转接口必须在服务端做，密钥不能进前端；网页版后续的服务端能力在同一代码库里加，不用迁移。代价是需要 Node 运行时来部署，这一点写进部署判据

## 2. 页面与路由

| 路径 | 文件 | 内容 |
|---|---|---|
| `/` | `app/page.tsx` | 门户首页，服务端渲染的静态页：首屏三张卡片：网页版（按钮跳 `/format`）、skill（安装命令与一句话用法）、Obsidian 插件（BRAT 仓库地址，社区上架后换）。下方放一屏产品说明与主题样张截图，便于搜索引擎收录 |
| `/format` | `app/format/page.tsx` | 在线排版页。左输入右预览。工具栏：主题选择、平台切换（公众号 / 知乎）、固定开头结尾开关与样式选择、标题输入、复制按钮；示例、清除本地数据和 GitHub 收入更多菜单 |
| `/api/transit/sign` | `app/api/transit/sign/route.ts` | 签发单个对象的上传条件，见 4.3 |
| `/api/transit/complete` | `app/api/transit/complete/route.ts` | 校验已上传对象，发放限时读取地址，见 4.3 |

浏览器边界：排版页整页是客户端组件，仍会被 Next.js 预渲染一次，所以 IndexedDB、`localStorage`、剪贴板 API 只在客户端生命周期（`useEffect` 或事件处理）里访问；需要跳过服务端渲染的部件用 `dynamic(() => import(...), { ssr: false })`，且这个调用放在客户端组件内，不从服务端组件直接用。core 的浏览器构建与高亮语言在 `/format` 里按需加载，门户不下载它们。

在线排版页布局：左侧 `textarea` 贴入 Markdown；右侧默认自适应预览，可切换手机宽度。窄屏用「编辑 / 预览」切换，同一时刻只展示一个工作区。文章 HTML 不使用页面壳的样式。

更多菜单提供新建文章、恢复上一稿和载入示例。替换当前文章前确认，并在本浏览器保留一份上一稿；只替换原文和标题，平台、主题及开头结尾设置保持不变。清除本地数据同时删除上一稿。

## 3. 数据流

```
Markdown 文本 + 已插入的本地图片(IndexedDB) + 页面配置(主题/平台/固定内容/标题)
      │
      ▼  core.prepare(input, { platform, fixed, resolver: BrowserAssetResolver })   异步
PreparedArticle { tree, images[], cover, warnings[], version }
      │
      ▼  core.render(prepared, { theme })                                               同步纯函数
RenderResult { html, images[], degraded[], placeholders[], stats }
      │
      ├─▶ 预览：iframe srcdoc = core 预览壳 + placeImages(result, PreviewStore)（图片用 blob: URL）
      │
      └─▶ 复制：placeImages(result, imageStore)
              公众号：imageStore = DataUrlStore
              知乎：  imageStore = TransitBucketStore（经 /api/transit/sign 直传 OSS，经 /api/transit/complete 换读取地址）
              → ClipboardItem { 'text/html', 'text/plain' }
```

- 每次输入、平台或固定内容变化都产生新的 `version`，`prepare` 与 `render` 的结果带着它回来；晚返回的旧版本直接丢弃，不覆盖新稿。切换主题只重跑 `render`
- 输入变化后 300ms 防抖再 `prepare`；主题、平台切换立即执行
- 一期在主线程执行。这不是性能结论，只是系列文章体量（数千字、十来张图）下的起点；出现可感知卡顿时把 `prepare` 与 `render` 移进 Web Worker，接口不变。是否需要 Worker 由实测决定，不预设字数或图片数阈值

## 4. 图片

### 4.1 本地图片进入文章

需求 17 与业务规则 6.2 要求：粘贴图片或选择本地文件能插入文章；只贴入了 Markdown 但本地路径无法读取时，指出缺失并提示补充。

- 在 `textarea` 里粘贴图片、拖入文件、或点「插入图片」选择文件，都走同一个入口：图片 blob 存入 IndexedDB，并在光标处插入 `![](jz-local://<assetId>)`。这个 URL 只在网页版内部有意义
- 两张映射表：`refs`（原始引用 → assetId）决定文章里哪一处引用对应哪张图，`blobs`（内容 SHA-256 → Blob）只做去重。用户补上一张文件时，绑定的是某一处具体的缺失引用，同名文件在不同目录也不会被自动当作同一张（Codex 评审 W4）；绑定并写入 IndexedDB 成功后，才把 Markdown 里的引用改写为 `jz-local://`
- 页面提供的 `BrowserAssetResolver` 把 `jz-local://` 解析为 `blob` 类资源；相对路径、绝对路径（如 `./images/a.png`、`/Users/...`）在浏览器里读不到文件，解析结果为「缺失」
- 缺失图片在预览里显示占位块；编辑区底部按引用显示「补图」按钮，直接选择对应文件，不弹二次确认窗口。
- 远程 `http(s)` 图片保留原地址；复制时按 4.2 处理
- 「清除本地数据」按钮删除 IndexedDB 与 `localStorage` 里的全部内容，并说明清除的是本浏览器的数据

IndexedDB 只存当前浏览器；刷新页面后 Markdown 文本从 `localStorage` 恢复、图片从 IndexedDB 恢复，两者按 `jz-local://` 键对上。原图保留在浏览器；用户选择、粘贴或拖入图片后立即规范化并上传 OSS，图片读取链接有效期为 7 天。上传失败保留本地图片并提供行内重试；正文编辑不被阻塞。

### 4.2 复制时图片怎么落地

core 定义 `ImageStore` 接口：给定规范化后的图片字节，返回可放进 HTML 的 `src` 与目标交付方式需要的附加属性。图片规范化只用 core 的 `ImageCodec` 与 `NormalizeProfile`（architecture.md 第 5 节），网页版不另写规则。按目标平台选实现：

| 平台 | 实现 | 行为 | 依据 |
|---|---|---|---|
| 公众号 | `DataUrlStore` | 用 Canvas 实现的 `ImageCodec` 按 `clipboard` 档规范化，再编码为 `data:image/...;base64,...` 写进 `src`。零服务端，图片不出浏览器 | my-toolbox 的公众号复制就是这条路，作者日常使用验证过粘贴后图片保留 |
| 知乎 | `TransitBucketStore` | 规范化后经 4.3 的两个接口上传并取得预签名读取地址写进 `src`；知乎编辑器粘贴时抓取并转存到 `zhimg` | my-toolbox 的知乎路径就是先把图片上传对象存储换成公网地址再复制，作者多次实际使用证实知乎编辑器粘贴后会转存图片 |

远程图片：公众号路径先尝试 `fetch` 拿字节转 data URL，跨域不允许时保留原地址并给 `IMAGE_REMOTE_KEPT` 警告；知乎路径直接保留原地址，由知乎编辑器抓取。保留原地址是降级：浏览器里能预览不等于平台保存后可见，工具栏对这类图片显示「未能处理，粘贴后请在平台里核对」，并允许用户补一份本地文件替换它。

图片入口旁简短标明临时存储期限，不展示内嵌、上传数量及远程地址等内部统计。按规范化内容摘要缓存中转结果，刷新、切平台与复制复用；缓存提前一天失效，之后从本地原图重新上传。

### 4.3 中转桶与两个接口

- 阿里云 OSS 独立 bucket：私有读写、不开列表、关闭版本控制、生命周期规则 7 天删除、CORS 只放行本站域名。未通过校验的对象不会成为可访问图片
- `POST /api/transit/sign`：入参图片 MIME 与字节数，出参 OSS 表单直传（PostObject）所需字段：policy、V4 签名、随机对象 key、5 分钟过期，`content-length-range` 限 10MB，`Content-Type` 限 `image/jpeg|png`，并带 `x-oss-forbid-overwrite: true`，保证同一凭证不能在校验后把对象换成别的内容。响应同时给一张服务端签名的票据（HMAC，含 key、大小、过期时间），供 `complete` 核对。OSS 密钥只在服务端环境变量里
- `POST /api/transit/complete`：入参票据。服务端核对票据签名与过期，用 HEAD 取对象实际大小并与票据比对，再读取对象字节校验：魔数是 JPEG 或 PNG、能解析出尺寸、像素规模在上限内、能被 sharp 解码。全部通过才返回一个 V4 预签名 GET 地址，用长期密钥签、有效期 7 天（OSS V4 预签名地址的上限）；签名只对 GET 有效。校验不过则删除对象并返回具体原因
- 说明文案分开写两件事：链接 7 天后失效；桶内对象按生命周期规则清理，清理任务按周期执行，不承诺到期那一刻所有副本已删除
- 限流不写业务代码：用部署平台或反向代理自带的按 IP 频率限制（Cloudflare Rate Limiting、Nginx `limit_req` 等），两个接口按 IP 每分钟与每天各设上限；bucket 侧设流量告警
- 两个路由处理器内部都是标准的 `(Request) => Promise<Response>` 函数，与 Next.js 无关的部分放 `lib/transit/`，方便单测，也方便将来搬到别的运行时

## 5. 剪贴板

- 用 `navigator.clipboard.write([new ClipboardItem({ 'text/html': htmlPromise, 'text/plain': textPromise })])`。写入调用发生在用户点击的同步调用链里，ClipboardItem 的值传 Promise，图片处理与上传在 Promise 内完成，这是 Safari 与 Chrome 都支持的异步写法。两个 MIME 共用同一个准备任务，不重复上传
- 公众号：点「复制到公众号」即写入，Promise 内做 data URL 内嵌
- 知乎：点「复制到知乎」直接写入，优先复用插图时已取得的 OSS 地址；旧稿或过期图片在准备正文时补传。取消上传确认和复制结果弹窗。复制过程中改稿会作废旧复制任务；图片上传独立于文章编辑，仍保留本地副本。
- `text/html` 是 core 的平台成品 HTML；`text/plain` 是成品的可见文本（不是 Markdown 原文，纯文本粘贴是降级，不冒充「导入 Markdown」）
- 两平台复制成功时按钮短暂显示「已复制」，随后恢复；失败在页面内显示具体原因与「重试复制」「手动复制」操作。
- 失败（浏览器不支持 ClipboardItem、权限被拒）时的兜底是「全选预览区复制」：预览 `iframe` 里已经是带图片的成品，浏览器原生的选区复制会带上富文本；选中后仅短暂提示复制快捷键，纯文本复制不算格式与图片完整。不再弹 HTML 源码文本框（Codex 评审 W1）

## 6. 预览

- 桌面顶栏合并为 60px 单行，平台选择与复制相邻；窄屏分两行，总高 108px。原文编辑区统一 16px 等宽字体。

- `iframe` 加 `sandbox`（只允许 `allow-same-origin` 以便 `blob:` 图片可用，不允许脚本、表单与顶层导航），`srcdoc` 由 core 的 `./preview` 预览壳加渲染输出组成，复用命令行、插件的预览壳，网页版关闭封面区。公众号预览壳模拟微信文章页：默认自适应宽度，可切换 375px 手机预览、白底、系统字体、顶部标题区（标题、账号名、日期）、正文区。名片等平台组件在预览里用占位块表示，占位块由 core 在 `placeholders` 里标出，预览壳负责画
- 封面：网页版只复制正文，不提供封面选择或预览封面；封面在目标平台设置。共享预览壳通过 `hideCover` 控制，其他客户端保持原有行为。
- 知乎预览壳套一份精简的知乎阅读样式（标题字号、正文 15px 行高 1.7、引用左边线、代码块底色、表格边框），正文用 core 的知乎结构输出；core 返回的 `degraded` 列表（h4 及更深标题降级、装饰样式丢弃、名片移除）在预览里逐条标出
- 预览壳里的图片用 `URL.createObjectURL(blob)`；预览与复制的差别只在图片的 `src` 与附加属性，其余 HTML 相同，满足「预览与推送用同一份输出」
- 编辑区保留可见字数；移除「复制前检查」、接口 HTML 预算、剪贴板体积、清理日志等开发诊断信息。复制路径不受公众号草稿 API 的 20000 字符上限约束。
- 原文和预览按原文行号双向同步滚动，点击预览正文定位到对应原文；链接点击和文字选区保持原有行为。行号标记只用于预览，自动复制与手动复制均不携带这些属性。

## 7. 固定内容

- 网页版只提供纯样式的开头结尾（需求 29）：内置几套样式模板，文案（作者名、口号、结尾话术、合集链接）在页面表单里填，存 `localStorage`。不含名片等需要账号资料的元素
- 模板与变量机制和本地形态相同（见 architecture.md 第 6 节），只是配置来源从用户目录变成浏览器存储
- 开头和结尾分别控制：开启后在开关下方显示各自的样式、文案字段，关闭后收起并保留已填内容；两个平台的设置分别保存。

## 8. 标题

网页版没有文件名，标题只用于预览壳与固定内容的 `{{title}}` 变量：工具栏一个标题输入框，留空时按业务规则视为缺省，含 `{{title}}` 的模板行不渲染，预览壳显示「未命名文章」。输入框旁提供「用正文一级标题」按钮，由用户主动点选，不静默把 H1 当标题（Codex 评审 W3）。复制内容不含标题，标题在平台编辑器里填写。

## 9. 工程

- 目录 `apps/web/`，用 `create-next-app` 初始化，App Router，TypeScript，Tailwind；独立 UI 组件按需引入（shadcn/ui 是候选，不锁定）；依赖 `@jinzhang/core` 的 `.`、`./preview`、`./browser` 三个入口，构建时核验产物里没有 Node 内置模块、sharp 与投递代码（architecture.md 第 3 节）
- 门户首页是服务端渲染的静态内容，构建时注入版本号与安装命令；排版页按第 2 节的浏览器边界处理
- 测试：core 的渲染由 core 自己的测试覆盖；网页版用 Vitest 测 `BrowserAssetResolver`、两张映射表与缺失引用绑定、`DataUrlStore`、`TransitBucketStore`（mock 两个接口）、任务版本作废、剪贴板载荷组装（mock ClipboardItem）、`lib/transit/` 的票据签发与对象校验；Playwright 一条端到端用例覆盖「贴入含本地图片的文章 → 补图 → 分别复制到两个平台」
- 部署：需要 Node 运行时（或平台对 Next.js 的原生支持）；判据是国内可访问；候选为国内云主机或容器加反向代理、Vercel、Cloudflare 的 opennextjs 适配；平台待定
