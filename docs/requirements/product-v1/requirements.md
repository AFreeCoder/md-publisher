## 1. 背景

### 1.1 真实需求

作者在 Obsidian 写技术文章，成稿后要发到两个主阵地：微信公众号「码农的自由之路」与知乎「AFreeCoder」。两个平台的编辑器都不接受 Markdown 原文，也不接受外站图片，每篇文章都要重复一遍「排版 → 传图 → 贴进后台 → 补标题封面 → 加固定的开头结尾」。这是纯粹的渠道成本，与文章价值无关。

现有工具 my-toolbox（本地网页）已经把公众号这条路走通了一半：多套主题、复制保样式、推送公众号草稿箱、公众号名片、开头结尾样式，固定样式中的文案可直接在页面配置。但它离「顺手」还有距离：工具不在写作发生的地方，要先起服务再去浏览器操作；知乎只有复制粘贴；封面只能是正文首图；开头结尾只有一套样式；预览看不到拼上固定内容之后的成品；公众号 IP 白名单靠手工代理；正文超 2 万字符靠压缩 HTML 兜底；配置目录、全局安装依赖等工程问题反复出现。

### 1.2 双重身份

本项目同时是《从 0 到上线：帮你把第一个产品发上线》系列的贯穿教学项目，全程公开、仓库即教材。这带来两条额外要求：范围要能按篇切成可验收的里程碑；每一步的取舍要能讲清楚理由。教学身份不改变产品目标，只约束交付方式。

## 2. 核心需求

### 2.1 从不可再分的事实出发

1. 作者的价值全部在内容里，排版与投递是渠道税。产品的价值就是把每篇的渠道税压到接近零，一次性的配置成本可以接受
2. 平台是围墙花园。文章必须在每个平台的墙内「重新物化」：用它接受的 HTML、放在它自己的图片存储里、填进它自己的字段。这些工作不可省略，只能决定由人做还是由工具做
3. 平台对自动化的开放程度不同。公众号有官方接口，但要求出口 IP 白名单；知乎没有发文接口，只能用本机登录态。集成策略必须按平台分别设计
4. 平台对样式的态度不同。公众号保留内联样式，主题真正起作用；知乎剥掉样式、套自己的阅读样式，只保留结构。主题与预览必须按平台区分承诺
5. 最终发布动作留给人。定时、标题微调、封面裁剪、话题选择都在平台后台完成，工具的责任止于草稿箱。个人主体的公众号也已经没有正式发布接口权限
6. 凭证等于账号控制权。AppSecret 和知乎登录态在本机保存，仅用于向对应目标平台认证，不交给本产品服务端；文章推送前要用户确认
7. 文章会被改。第一次推送之后还会改稿重推，重推必须更新同一份草稿而不是堆出重复草稿
8. 品牌外观是固定的。每篇文章的开头、结尾、名片、往期文章入口一样，只有正文在变。固定部分应该配置一次、每篇自动拼上
9. 输入必须是干净的原生 Markdown。工具不能依赖任何编辑器的私有属性，否则等于强制用户用 Obsidian，网页版也无从渲染
10. 作者在 Obsidian 里写作，在终端里和 agent 协作。能力必须出现在这两个地方；网页版服务的是不用这两者的读者

### 2.2 核心需求的一句话表述

把一篇 Markdown 在写完它的地方，用一个动作，变成各个平台草稿箱里可以直接发布的成品；成品结构与图片完整、公众号外观与预览一致、改稿后可重复推送、凭证本地保存。

### 2.3 需求原语

需求拆到不可再分，是五个原语加两个附属物；功能清单由此推导，新增平台按同一结构复制：

- 单一事实源：一个原生 Markdown 文件与它引用的图片。产物由原文、单独设置的封面与已选配置生成，可以重新生成，不回写源文件，不要求在原稿里维护平台专用属性
- 方言转换：把 Markdown 变成目标平台接受的 HTML，结构不丢；公众号外观由排版样式决定，知乎外观由知乎决定
- 资源归位：图片必须进入目标平台自己的存储，这是独立于渲染的一步
- 投递：把成品放进平台草稿箱。官方接口优先，没有接口走本机登录态，剪贴板是兜底；重推更新同一草稿
- 身份与信任：凭证在本机保存，只向对应目标平台认证，不交给本产品服务端；推送前确认；错误可读可处理
- 附属：品牌包装。按平台配置开头与结尾，渲染时自动组合
- 附属：文章信息。标题取文件名；封面可单独设置，未设置时退回正文首图；其余不需要填写

### 2.4 产品原则

- 就地发布：Obsidian 插件和 skill 是主形态，网页版只做门户与在线排版
- 本地优先：凭证在本机保存、不交给本产品服务端；正文在本地处理，用户确认推送后发往所选目标平台。网页版不接触账号凭证、不做一键推送；若复制粘贴需要临时图片中转，应在上传前说明仅上传用户所选图片及其保留期限
- 原生输入：只认标准 Markdown，文件即文章
- 一次配置、每篇零配置：账号、包装、主题、推送平台配置一次；单篇差异在推送时调整
- 可预览、可确认、可重复：推送前看到成品（公众号所见即所得，知乎看结构）；推送要确认；重推更新同一草稿
- 渠道可扩展：新增平台等于新增一套「方言 + 归位 + 投递 + 包装模板」，壳不改

## 3. 目标用户与场景

### 3.1 用户

- 主用户：作者本人。Obsidian 写作，技术内容，公众号与知乎双发，日常在终端与 agent 协作，每篇封面单独生成
- 次用户：系列读者与独立开发者。技术背景，多数有公众号，部分用 Obsidian，部分只想贴一段 Markdown 复制走
- 不服务：团队协作、多账号运营、需要审批流的机构号

### 3.2 场景

| 编号 | 场景 | 形态 | 用户动作 | 期望结果 |
|---|---|---|---|---|
| S1 | Obsidian 内成稿后发布 | Obsidian 插件 | 打开预览看成品，设置封面，点推送，确认 | 配置里选中的平台草稿箱各出现一篇，公众号外观与预览一致，知乎结构完整，图片齐全，封面正确，开头结尾已拼好 |
| S2 | 终端或 agent 会话中发布 | skill | 对 agent 说「把这篇发到公众号和知乎草稿箱」 | agent 先体检再推送，展示确认信息，返回草稿箱位置与警告 |
| S3 | 改稿后重推 | 插件或 skill | 再次推送 | 按用户决定更新同一份草稿，不产生重复草稿 |
| S4 | 不用 Obsidian 的读者 | 网页版 | 贴 Markdown，粘贴或选择本地图片补齐引用，选主题，可选一段纯样式的开头结尾，复制到公众号或知乎编辑器 | 粘贴后公众号样式与预览一致，知乎结构完整，图片可见 |
| S5 | 首次配置 | 插件或 skill | 填公众号 AppID 与 AppSecret，按引导加 IP 白名单；登录知乎；配置开头结尾与默认推送平台 | 配置一次后每篇零配置；出口 IP 变化时得到明确提示 |
| S6 | 推送失败 | 插件或 skill | 看到错误 | 错误说明是什么、怎么处理，不出现原始接口报文 |
| S7 | 推送不可用时改走复制粘贴 | 插件、skill 或网页版 | 某平台推送失败或没配置，一键复制为该平台的正文格式，到平台编辑器粘贴 | 正文结构与图片完整；封面在平台编辑器里单独设置；提示写明是「已复制」而不是「草稿已保存」 |

## 4. 目标与非目标

### 4.1 一期目标

| 编号 | 目标 | 验收方向 |
|---|---|---|
| G1 | 一篇含本地图片的原生 Markdown 从 Obsidian 或 skill 一个动作进入公众号草稿箱 | 草稿箱内标题、封面、正文样式、图片与预览一致；正文图片全部可见 |
| G2 | 同一篇一个动作进入知乎草稿箱 | 知乎草稿标题、封面、正文结构、图片完整；一键推送不可行时退为一键复制后粘贴结构完整，封面由用户在平台编辑器中设置 |
| G3 | 开头、结尾、名片、往期文章入口按平台配置自动拼装 | 两个平台各自的固定内容出现在正确位置；支持开启或关闭 |
| G4 | 改稿重推更新同一草稿 | 用户确认重推后更新原草稿，草稿数量不变 |
| G5 | 网页版完成贴入、预览、复制 | 粘贴到两个平台编辑器后样式或结构与图片可用；无账号、无数据库 |

### 4.2 非目标

- 正式发布、群发、定时发布；工具止于草稿箱
- 多账号与账号切换；多图文；图片消息
- 用户体系、支付、云端保存文章；带登录的 SaaS
- 自建永久图床；要求用户自带图床
- 完整在线写作编辑器（网页版仅提供 Markdown 输入、图片插入、排版预览与复制）；浏览器扩展；桌面客户端；本地 app
- 文章级元数据（frontmatter 或任何编辑器私有属性）；摘要设置；作者设置；原文链接
- 公众号外链转参考链接或脚注；深色模式；导出 HTML 或 Markdown
- 知乎排版样式选择；知乎话题；系列导读的自动目录
- 小红书、掘金、头条等其他平台（结构上预留）
- Obsidian 移动端
- 评论管理、数据统计、AI 写作与配图

功能清单只写用户能做什么、得到什么；实现方案见设计文档。分期依据 issue #1 快照 5 与快照 7：一期 = 作者自用闭环能用且网页版能上线；二期 = 一期上线后迭代；一期内部的交付批次属执行安排，见 issue #1。

## 6. 业务规则

规则只写用户可感知的行为；实现机制进设计文档。

### 6.1 文章信息

- 标题取文件名（去扩展名）。正文首个一级标题与文件名相同时不重复输出。推送公众号时标题超过 32 字给警告，不阻止（32 字是接口文档的要求，实测更长也能提交）
- 公众号与知乎均支持封面；知乎文章的题图在本产品中统一称为封面。封面优先用单独设置的图；未设置时退回正文第一张图，固定开头里的图片不算候选。两者都没有时，按目标平台的封面要求分别提示或阻止，不将公众号的必填校验直接套用到知乎
- 不做摘要与作者设置，推送时不填摘要与作者字段，摘要由公众号自动抓取正文前 54 字

### 6.2 输入与图片

- 只认标准 Markdown 与常用扩展；编辑器私有写法按普通文本处理并提示，Obsidian 的图片嵌入与双链由插件在交给渲染前处理
- 图片来源支持相对路径、绝对路径、网络地址；远程图片下载失败要指出是哪一张
- 网页版支持粘贴图片或选择本地图片文件并插入文章；仅贴入 Markdown 中的本地路径不能读取对应文件，缺失图片时指出具体引用并提示用户补充。图片上传与复制后的可用性遵循同一套数据去向说明
- 推送时图片自动进入目标平台，用户不需要自备图床；平台不接受的格式或大小自动处理，处理不了的图片（如无法转换的 SVG）阻止并指出是哪一张
- 同一张图不重复上传；同一张封面重复推送时复用

### 6.3 排版与预览

- 主题只作用于公众号；知乎正文用知乎自己的样式，不提供主题选择
- 公众号预览是完整成品（含固定内容与封面），所见即所得；名片、合集卡片等只有在公众号里才渲染的平台组件，预览里用占位块表示并标注以公众号实际渲染为准
- 知乎预览展示封面与正文结构，按知乎阅读样式模拟，只承诺内容与结构一致；会被降级或丢弃的内容（三级以下标题、装饰样式、名片）在预览里标出
- 公众号预览与草稿一致：表格、代码块、列表、引用、中文标点不走样
- 正文接近公众号 2 万字符上限时提前提示，给出压缩或拆分建议；超限时阻止并报出实际字符数
- 公众号外链不做处理；微信会去掉非公众号链接的地址，读者只看到链接文字，这一点在文档里说明
- 知乎保留文章结构（标题层级、强调、引用、列表、代码、表格、图片）；标题层级映射到知乎支持的两级
- 预览与推送使用同一份输出
- 微信保存后可能丢失代码块空格、编辑器规则会变，这类平台侧限制在文档与结果提示中说明，不承诺完全保真

### 6.4 固定内容

- 支持按平台配置开头、结尾的内容与样式，页面可直接修改固定样式中的文案等内容；支持 Markdown 或 HTML 内容；公众号可含图片、名片，知乎只支持文字、图片、链接；变量至少支持标题、日期，变量缺省时该行不渲染
- 公众号名片是开头或结尾样式内容的一部分：样式里放了名片就展示，没放就不展示，不做额外的位置或去重逻辑；通过接口提交后若被平台过滤，给出警告而不是失败
- 「往期文章」是固定结尾里的一种样式块，放公众号合集链接（知乎侧放专栏或汇总篇链接）；合集链接经接口提交后是否可点待实测
- 固定开头、结尾支持开启或关闭；保存多套头尾配置留到二期
- 网页版只提供纯样式的固定开头结尾，不含名片等需要账号资料的元素

### 6.5 推送

- 单账号、单篇图文；工具止于草稿箱，不调用任何发布接口
- 同一源文件首次推送创建草稿；是否重推由用户决定，确认后将当前文章内容和配置更新到对应平台的原草稿，不做内容变化检测或自动跳过；原草稿已删除或已发布、无法继续更新时，新建草稿并提示
- 推送前展示目标平台与账号、标题、封面缩略、图片数量、正文字符数、开头结尾是否启用，用户确认后才出站
- 推送前体检只读、无副作用：按所选平台分别检查账号凭证或登录态、封面、标题与正文长度、图片格式与大小；公众号另检查出口 IP 白名单，未选择公众号时不要求其配置；各平台分别列出已知且可检查的阻塞项，结果可被 agent 读取；体检通过不保证后续推送成功，网络、登录态或平台限制变化导致失败时明确报告原因
- 成功时给出草稿箱入口与警告列表（如名片被过滤）；失败时给出原因与下一步动作；超时或中断导致无法判断平台是否已写入时，明确告知先去草稿箱确认，不自动重试创建
- 失败时给出原因；平台错误码逐条翻译为用户动作不在一期范围，后续遇到具体报错再补
- 默认推送平台在配置里设置，一次动作推所有选中平台并分别报告，单次可临时改；一个平台失败不影响也不重发已成功的平台
- 任一平台推送不可用时，可一键复制该平台正文格式粘贴到编辑器；封面在平台编辑器中单独设置，复制正文不代表已设置封面

### 6.6 账号与配置

- 配置分公共配置（默认排版样式、固定内容、默认推送平台）与分平台配置（公众号凭证、知乎登录态）；skill 与 Obsidian 插件共用同一份，复制到另一台机器可直接使用
- AppID、AppSecret、知乎登录态只存用户目录，权限仅当前用户可读写；仅用于向对应目标平台认证，不交给本产品服务端；不进日志、错误信息、任何网页产物，也不放在会随笔记同步的目录里
- IP 白名单：配置时显示当前出口 IP 并可复制，给出后台入口；推送遇白名单错误时再次提示；可配置固定出口；文档写清家庭宽带 IP 会变。白名单摩擦不由我们托管解决，不做转发服务
- 知乎登录：可登录、查看登录状态与账号、退出；登录态失效时提示重新登录

### 6.7 可扩展性

新增平台的工作量限定为新增一套「方言 + 归位 + 投递 + 包装模板」，网页版、skill、插件不因新增平台改动壳的结构。小红书是第一个候选验证对象，不进一期与二期。

## 7. 平台的业务级约束

### 7.1 微信公众号：官方接口路线

已在 my-toolbox 上跑通，沿用。

| 项目 | 约束 | 来源 |
|---|---|---|
| 标题 | 官方文档 32 字（2025-12 起明确）；实测 64 字可提交 | 官方 draft/add 文档；2026-08-18 实测 |
| 作者 | 16 字；本产品不填 | 官方文档 |
| 摘要 | 120 字；缺省抓正文前 54 字 | 官方文档 |
| 正文 | 少于 2 万字符且小于 1M；JS 被去除；外部图片地址被过滤；非公众号链接的地址被去掉；只保留内联样式 | 官方文档；同类项目共识 |
| 正文图片 | 只能来自 uploadimg 接口；jpg 与 png；1MB 以内；不占素材库 10 万张配额 | 官方文档 |
| 封面 | 永久素材；占素材配额；裁剪比例 2.35:1 与 1:1 | 官方文档 |
| 凭证 | 稳定版 access_token 有效期 7200 秒，普通模式重复调用不刷新 | 官方文档 |
| 出口 IP | 必须加入公众号后台 IP 白名单，否则报 40164；无关闭开关 | 官方文档 |
| 正式发布 | 2025 年 7 月起个人主体账号、企业主体未认证账号、不支持认证的账号被回收发布类接口权限，不能再通过接口正式发布或群发；草稿与素材接口不在回收之列 | 官方发布能力指南；2025-06-30 官方社区答复 |
| 账号前提 | 草稿、素材、凭证接口公众号与服务号均可调用；未认证订阅号是否受限待实测 | 官方各接口「适用范围」 |

### 7.2 知乎：本机登录态路线

知乎官方开放平台、官方 CLI 与 MCP 只有搜索、热榜、直答这类只读能力，没有发文接口（2026-09-05 核对其全部文档）。一期用本机登录态调用知乎网页端使用的接口，只创建和更新草稿，不发布。这条路已有 Obsidian 插件持续一年可用。约束与风险：

- 知乎剥掉内联样式，正文只保留结构：两级标题、强调、引用、列表、代码、表格、图片；主题不起作用
- 登录态有有效期，会因风控失效；高频调用触发验证；产品必须能检查状态、引导重新登录
- 接口非官方，可能变动；任何一步失败都要能退到剪贴板路线
- 草稿要记录草稿标识并在重推时更新，否则会重复建文
- 具体机制（登录方式、图片处理、候补路线）留到设计阶段

### 7.3 剪贴板路线（两平台通用兜底）

两个平台的编辑器粘贴时会把可访问的外链图片转存到自己的服务器，图片只需活到被转存。网页版依赖这条路线；本地形态在推送不可用时也用它。

## 8. 验收方向

不写测试用例，只定验收判据。

- 标准测试文章：一篇含多级标题、嵌套列表、表格、代码块、引用、脚注、本地图片三张（含一张重复、一张 webp）、远程图片一张的原生 Markdown，文件名即标题，在两个平台草稿箱逐项核对结构、图片、封面、开头结尾、名片、往期文章入口；公众号另核对样式与预览一致，知乎核对结构与预览标注一致
- 封面：单独设置与退回首图两种情况各推一次，两个平台封面正确
- 网页图片输入：粘贴图片与选择本地文件均可插入文章；仅有本地路径但未提供文件时能指出缺失图片，补齐后预览与复制到平台编辑器的图片可见
- 反向路径：一张无法处理的图片（如无法转换的 SVG）触发阻止并指出是哪一张；一篇接近 2 万字符的文章触发提前提示；固定内容关闭后推送不带开头结尾
- 复制粘贴兜底：任一平台改走复制粘贴，粘贴到编辑器后正文结构与图片完整，提示写明是「已复制」而不是「草稿已保存」
- 推送前体检：能发现已知且可检查的阻塞项，提示与实际问题一致；体检通过后若推送失败，明确报告原因，不误报成功
- 重推：用户确认重推后，当前文章内容和配置更新到对应平台原草稿，草稿数量不变；即使内容未改也按用户决定更新；原草稿已删除或已发布、无法继续更新时，新建草稿并提示
- 凭证与数据去向：仓库、网页产物、日志、错误信息中搜不到 AppSecret 与知乎登录态；凭证不交给本产品服务端；网页版无任何凭证输入；正文在确认推送后发往目标平台，若使用临时图片中转，上传前已说明所选图片的去向及保留期限
- 效率：首次配置含白名单 10 分钟内完成；日常一篇文章从「写完」到「两个平台草稿箱就绪」人工操作 1 分钟内
- 一致性：同一原文、同一目标平台、同一配置下，网页版、skill、插件共有能力的渲染结果一致；名片等入口特有能力分别验收，预览占位块不替代平台实际组件的验收
